# 早高峰秒杀页面渲染优化方案

主要考察**静态化方案、缓存策略、性能优化和高并发架构设计**

## 核心思路：静态化 + CDN + 限流降级

秒杀页面的特点是：**读多写少、瞬时流量大、数据一致性要求相对宽松**（库存最终一致即可）。

---

### 1. 页面静态化（最关键）

**原则：让请求尽量在CDN层解决，不回源到后端。**

- **全页静态化**：将商品详情页提前生成为纯HTML（模板引擎预渲染），部署到CDN节点
- **动静分离**：静态资源（JS/CSS/图片）与动态数据（库存、价格、倒计时）分离
- **ESI/SSI**：边缘侧包含，在CDN层组装页面片段

### 2. 数据动态化方案

静态页面需要获取实时数据（库存状态、秒杀按钮状态）：

**关键点**：状态接口要做**请求合并/批量处理**，避免N个用户同时打爆数据库。

| 方案 | 实现 | 适用场景 |
| --- | --- | --- |
| **轮询+缓存** | 前端定时请求状态接口，后端Redis缓存，设置短TTL（1-2秒） | 通用方案 |
| **WebSocket推送** | 建立长连接，库存变化主动推送 | 实时性要求高 |
| **客户端倒计时** | 下发服务器时间戳，前端本地倒计时，到点再请求 | 减少无效请求 |

### 3. CDN与边缘计算

- **CDN预热**：活动开始前，将页面推送到所有CDN节点
- **边缘渲染**：利用CDN边缘节点能力（如阿里云ESA、Cloudflare Workers），在离用户最近的地方生成动态内容

### 4. 前端渲染优化

```javascript
// 1. 骨架屏优先展示，提升感知性能
// 2. 关键CSS内联，减少阻塞
// 3. 图片懒加载 + WebP格式
// 4. 按钮防重复提交（节流/禁用）
// 5. 本地缓存静态资源（强缓存 + hash指纹）
```

**降级策略**：
- CDN故障 → 切换到备用CDN或源站静态服务器
- 接口超时 → 展示缓存数据 + "刷新重试"按钮
- 流量突增 → 开启排队页面（类似12306）

---

## 面试加分点

1. **灰度发布**：秒杀页面先小流量验证，再全量放开
2. **监控告警**：QPS、RT、错误率实时监控，自动熔断
3. **压测数据**：提前用JMeter/自研压测工具模拟峰值流量（如10万QPS）
4. **用户体验**：倒计时同步服务器时间、按钮点击后立即置灰防重复

**一句话总结**：秒杀页面渲染的核心是**"能静态就静态，不能静态就缓存，不能缓存就限流"**，通过CDN承接90%以上的流量，后端只处理真正的下单请求。

# 早高峰秒杀页面渲染优化方案

主要考察静态化、缓存策略、前端性能和高并发保护。

核心原则：

- 公共内容尽量静态化，并前置到 CDN。
- 动态状态使用短缓存，合并回源。
- 用户操作才触发动态请求。
- 页面展示允许短暂延迟，交易数据必须强一致。
- 前端降低无效请求，后端负责限流、排队和交易正确性。

## 一、总体架构

秒杀页面的流量特点是：读取量极大，写入集中在活动开始瞬间。

请求按层处理：

1. 浏览器缓存承接静态资源。
2. CDN 承接公共页面和公共状态。
3. Redis 或本地缓存承接热点状态。
4. 只有真正参与秒杀和下单的请求进入交易系统。

用户信息、订单状态、优惠资格等个性化内容不能进入公共缓存。页面采用静态壳加动态组件的方式：

- 商品信息、活动规则、页面结构和基础样式预渲染为 HTML。
- 库存状态、秒杀按钮、用户信息通过独立接口更新。
- 动态区域局部刷新，不重新渲染整页。

## 二、页面静态化

公共商品详情页提前使用模板引擎预渲染成 HTML，并部署到 CDN。

具体策略：

- 公共页面全量静态化。
- 登录态和个人数据动静分离。
- HTML 使用版本化路径，发布时原子切换。
- HTML 使用短 TTL 或 ETag，保证活动配置可以更新。
- 带 hash 的 JS、CSS、图片使用长期强缓存。
- 私有数据使用 `private` 或 `no-store`，禁止进入共享缓存。

ESI 需要 CDN 明确支持。SSI 通常由源站 Web 服务器处理，不能默认所有 CDN 都能在边缘组装。边缘函数只处理轻量公共逻辑，不在边缘直接查询数据库。

## 三、动态状态与请求控制

库存和按钮状态使用粗粒度状态，例如“未开始、进行中、已售罄、排队中”，不需要向所有用户展示精确库存。

前端使用服务器时间偏移计算倒计时。根据接口响应时间估算时钟偏移，避免客户端时间不准导致提前或延迟开放。

开售前不持续高频轮询。用户点击时再请求状态。

状态接口采用以下策略：

- 使用公共缓存键，避免按用户缓存。
- 使用短 TTL，配合 `stale-while-revalidate`、ETag 和 304。
- 请求加入随机抖动和退避，避免所有用户同时请求。
- 页面进入后台后停止轮询。
- 热点 key 使用 single-flight 或分布式锁合并回源。
- Redis 失效时使用短暂过期数据或本地缓存兜底。

WebSocket 或 SSE 只用于推送“即将开始、已开售、已售罄”等状态变化。大规模用户下维护长连接成本较高，不适合持续推送精确库存。

## 四、CDN 与边缘计算

CDN 负责承接绝大部分公共读流量。具体命中比例以压测结果为准，不需要固定写成 90%。

优化措施：

- 活动前预热页面和静态资源。
- 使用分层缓存和 origin shield，减少源站回源。
- CDN 缓存键保持稳定，不加入随机用户标识。
- 使用 WAF、Bot 防护和入口限流。
- 多 CDN 健康检查和流量切换。
- 备用 CDN 尽量保持热缓存，避免切换时全部回源。

CDN 预热不代表所有节点立即有缓存。实际效果仍取决于分层缓存、节点调度和缓存失效策略。

## 五、前端渲染优化

前端优先保证首屏内容和秒杀按钮尽快可用。

- 静态 HTML 直接展示页面内容。
- 骨架屏只用于尚未完成的动态区域。
- 关键 CSS 内联，但控制体积。
- JS 按路由和组件拆分，延迟加载非关键代码。
- 首屏主图使用 `preload`、`fetchpriority="high"`，不能懒加载。
- 非首屏图片懒加载，并设置宽高避免布局跳动。
- 图片使用 WebP 或 AVIF，同时保留兼容格式。
- 倒计时根据服务器时间偏移计算。
- 页面重新可见时重新校准倒计时。

按钮点击后立即进入 pending 状态，防止重复点击。按钮置灰只是交互保护，服务端仍需使用幂等令牌和请求去重。

请求失败后不能永久禁用按钮。应在有限次数内使用退避重试，并允许用户重新操作。

## 六、交易正确性

页面展示可以最终一致，交易库存不能最终一致。

下单链路必须保证：

- Redis Lua 原子扣减或库存预留，防止超卖。
- 使用幂等键防止重复下单。
- 消息队列异步落库，削峰并保证最终一致。
- 服务端重新校验价格、库存和活动资格。
- 按用户、设备、商品和 IP 设置限流。
- 对异常流量启用风险控制和验证码。

前端静态页面中的库存和价格只用于展示，不能作为交易依据。

## 七、降级策略

### CDN 故障

切换到备用 CDN、对象存储静态站点或源站静态服务器。

源站必须配置并发上限、限流和熔断，避免故障切换时被全部流量打满。

### 状态接口超时

展示最近缓存状态，并明确标记数据更新时间。

自动使用随机退避重试，不能只提供“立即刷新”按钮，否则恢复瞬间会形成二次请求洪峰。

### 缓存击穿

使用 single-flight、分布式锁、逻辑过期和本地短缓存保护回源链路。

### 流量突增

在 CDN 或入口层开启排队页，发放准入令牌，避免所有用户直接进入应用层。

### 数据不可用

展示内容可以降级。库存状态未知时，交易必须失败关闭，不能继续接受下单。

## 八、压测与监控

压测目标要拆分：

- 页面访问 QPS。
- 状态接口 QPS。
- 下单链路 QPS。
- WebSocket 或少量的长连接数。
- CDN 回源 QPS。

重点测试冷缓存、缓存击穿、故障切换和活动开始瞬间。

监控指标包括：

- QPS、p95、p99、错误率。
- CDN 命中率和回源 QPS。
- Redis 命中率、热点 key 和阻塞情况。
- 下单成功率和重复请求率。
- LCP、INP、CLS、JS 错误率等前端真实用户指标。

灰度发布使用版本化 HTML，先按区域或小流量放开，再全量切换。保留快速回滚和功能开关。

## 一句话总结

> 公共页面静态化并交给 CDN；公共状态在边缘短缓存；倒计时本地计算，用户操作再请求；展示数据可以最终一致，交易库存必须强一致；通过限流、排队、幂等和降级保证系统不被击穿。
